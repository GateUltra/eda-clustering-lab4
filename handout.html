MODULE 01-05 / TEACHING NOTES

Size-constrained agglomerative clustering

A reproducible greedy method for grouping strongly connected cells subject to a hard size limit.

1. Model and terminology

Use an undirected weighted graph. A node represents a cell. A nonnegative edge weight represents connectivity strength, and a positive node size can represent cell area. A cluster is a set of nodes. A cluster’s size is the sum of its node sizes.

TermMeaning in this lesson
target KDesired final number of clusters, not a guaranteed outcome.
capacityMaximum allowed total size of each cluster; absent means unbounded.
affinitySum of original edge weights joining two current clusters.
contractionReplace two clusters with their union, sum sizes, and update connections.
cutsizeSum of weights of edges crossing between clusters, each undirected edge counted once.

A real netlist may contain multi-pin nets represented as hyperedges. This lab intentionally uses a graph model; it is not a production placement or partitioning flow.

2. Algorithm and deterministic tie-break

  1. Start with one singleton cluster per node. Validate inputs and reject a singleton that already exceeds capacity.
  2. If the current cluster count equals K, stop.
  3. Compute affinity for every current cluster pair and retain only positive-affinity pairs.
  4. Sort by decreasing affinity. For equal affinity, compare a canonical pair of sorted member lists lexicographically.
  5. Check capacity before merging. Skip an illegal pair and keep checking lower-ranked candidates.
  6. Merge the strongest legal pair. Update membership, sizes and affinities after contraction, then repeat.
  7. If no legal positive-affinity pair remains, stop and report the actual result.

For the tie-break, sort each cluster’s labels, then place the lexicographically smaller member list first in the pair. Compare first lists, then second lists; a proper prefix is smaller than its extension. For example, ([A,B],[C]) precedes ([D],[E]). The supplied code restricts labels to ASCII letters, digits, underscores and hyphens, starting with a letter, so Python and JavaScript use the same ordering.

Zero-affinity merges are deliberately excluded, even if they could reduce the cluster count. In a disconnected graph, this stopping policy may prevent reaching a feasible target. The reference recomputes affinities from original edges and current membership; this is equivalent to summing parallel edges during contraction for this model.

Upstream generates cluster names such as C0 and C1. Our member-list rule is easier to follow and avoids dependence on synthetic names. Equal-affinity merge orders may differ on other graphs. We claim consistency within this package, not universal trace equivalence with upstream.

3. The original five-node example

Every node has size 1. Edges: AB=5, AC=1, BC=4, CD=2, CE=1, DE=5. The initial cutsize is 18 because every node starts in a different cluster.

AB and DE tie at affinity 5. The tie-break chooses A+B first, giving cluster AB of size 2 and cutsize 13. After contraction, affinity(AB,C)=AC+BC=1+4=5. The internal AB edge is removed from the candidate set.

K=2, capacity=2

At the final state, AB–C has affinity 5 and C–DE has affinity 3. Both merges exceed capacity 2. AB–DE has affinity 0 and is not a candidate. Crossing edges are AC, BC, CD and CE: 1+4+2+1=8.

The result has cluster sizes 2,1,2 and complies with capacity. It has three clusters, so target K=2 was not reached. Five unit-size nodes cannot fit into two clusters of capacity two: total size 5 exceeds total available capacity 4. This is an infeasible target, not merely a poor greedy choice.

K=2, capacity=3 or no capacity limit

The trace under our tie-break is A+B, then AB+C, then D+E. Cutsize follows 18,13,8,3. In the middle tie, ([A,B],[C]) precedes ([D],[E]). The result is ABC | DE, with sizes 3 and 2. Only CD and CE cross, so cutsize is 2+1=3.

4. Feasibility is different from greedy success

Feasible target, greedy failure. Use sizes A=2, B=2, C=1, D=1; edges CD=10, AC=4, BD=4; target K=2; capacity=3. Greedy first merges C+D. The resulting three clusters each have size 2, so no pair can merge. Yet AC | BD has two size-3 clusters and is feasible. The greedy algorithm does not split a previous cluster or reconsider earlier decisions.

Legal but suboptimal. Use four unit-size nodes; edges AB=10, AC=9, BD=9, CD=1; K=2; capacity=2. Greedy returns AB | CD with cutsize 18. AC | BD has cutsize 11. Exhaustive enumeration of all two-cluster partitions confirms 11 as the optimum for this example.

Total size ≤ K × capacity is a necessary condition for capacity feasibility, but it is not sufficient for arbitrary indivisible node sizes. Even when a feasible partition exists, this greedy process may miss it. Even when it reaches K, its cutsize may be suboptimal.

5. Implementation exercise

Implement solve(graph, k, capacity) in source/exercise.py. Maintain sorted member lists, compute affinities, check capacity, choose a deterministic pair, contract, and report metrics. Do not import the completed reference into your solution.

python source/check_exercise.py --impl source/exercise.py
python source/reference.py --k 2 --capacity 2
python source/reference.py --case greedy_trap --k 2 --capacity 3
python source/reference.py --case suboptimal --k 2 --capacity 2
python source/verify.py

Required output fields are clusters, actual_count, cutsize, sizes, capacity_compliant, and target_reached. The reference also records every candidate list, each chosen merge and the stopping reason.

The reference accepts nonnegative edge weights, supports parallel edges by summation, rejects self-loops and invalid sizes, and uses exact floating-point capacity comparisons without an implicit tolerance. Integer examples avoid numerical ambiguity. For larger designs, a priority queue can improve performance, but it must invalidate stale candidates correctly.
